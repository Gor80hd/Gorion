## Исправлено

### Системный прокси

1. Неудачное применение на любой службе запускает откат. Неудачный откат сохраняет журнал и блокирует его перезапись новым подключением.
2. HTTP, HTTPS и SOCKS восстанавливаются независимо. Изменение пользователем одного endpoint не даёт права перезаписать остальные настройки пользователя.
3. Ошибка восстановления одного endpoint не прекращает попытки отключить остальные. Если запись исходного endpoint не удалась, выполняется аварийное выключение его переключателя.
4. Исключения восстанавливаются только при совпадении с применённым Gorion списком. Пустой список передаётся networksetup как `Empty`.
5. PAC и автоматическое обнаружение прокси сохраняются, отключаются на время подключения и восстанавливаются. Изменённый URL PAC не перезаписывается.
6. Запись журнала выполняется через временный файл и rename. Повреждённый или недоступный журнал не считается успешным восстановлением.
7. Ошибки восстановления доходят до вызывающего кода, вместо успешного результата при оставшемся прокси.

### Процесс и аварийное завершение

1. После неожиданного завершения ядра маркер процесса сохраняется до восстановления прокси.
2. После отправки SIGTERM осиротевшему процессу проверяется фактическое завершение. Успешная отправка сигнала сама по себе больше не считается остановкой.
3. Runtime другого работающего экземпляра приложения не считается осиротевшим.
4. Ошибка ядра во время применения прокси не возвращается как успешное подключение.
5. POSIX guard проверяет принадлежность маркера на каждом проходе и идентичность процесса перед сигналом. Старый guard не должен завершать новое подключение.
6. Guard отключает каждый управляемый тип прокси отдельно, сохраняет журналы и повторяет неудачные записи.
7. Для system proxy создаётся `~/Library/LaunchAgents/app.gorion.proxy-recovery.plist`. При следующем входе в macOS он запускает очистку оставшихся endpoints, даже если после потери питания приложение ещё не открывали. До входа пользователя эта защита не выполняется.
8. Таймаут внешней команды охватывает также чтение stdout/stderr. Унаследованные дочерними процессами потоки больше не должны удерживать команду после дедлайна.

### TUN и конфигурации

1. macOS сама назначает имя utun вместо неподходящего `gorion-tun`.
2. Сохраняется auto_detect_interface для предотвращения петли маршрутизации.
3. Убрано автоматическое добавление устаревшего block outbound. Правила блокировки используют action=reject.
4. TUN получает sniff и hijack-dns. Если в шаблоне нет DNS-настроек, добавляются DNS через VPN и отдельный локальный bootstrap для разрешения имени самого VPN-сервера. Заданный шаблоном DNS сохраняется.
5. Перед запуском процесса выполняется `sing-box check`.
6. Неподдерживаемый транспорт ссылки больше не подменяется обычным TCP молча.

### Привилегированный помощник

1. Клиент передаёт PID владельца TUN. На macOS помощник проверяет PID вместе со временем запуска/именем процесса и останавливает runtime после исчезновения владельца.
2. Клиент отслеживает завершение runtime в помощнике и передаёт событие в интерфейс.
3. Изменяющие запросы помощника выполняются последовательно; чтение HTTP-ответов и тел запросов ограничено по времени.
4. Добавлена версия протокола: старый macOS helper не принимается за совместимый с новой логикой владения.
5. Установщик копирует bundle помощника в root-owned каталог. LaunchDaemon не ссылается на изменяемый пользовательский build-каталог. У существующих файлов поддержки снимается групповая/общая запись.
6. Файл состояния с токеном публикуется атомарно после установки прав. Ошибка установки прав больше не игнорируется.

## Известные ограничения

- XHTTP не поддерживается встроенным sing-box 1.13.5. Это подтверждено самим бинарником (`unknown transport type: xhttp`) и отдельным тестом импортёра. Для такого профиля нужен Xray backend; он в этом изменении не добавлен.
- Для существующего прокси с аутентификацией системный режим останавливается до изменения настроек: networksetup не предоставляет пароль для надёжного восстановления. Можно использовать локальный mixed-режим.
- На машине пользователя работает другой VPN, необходимый для связи с Codex. Полный TUN-тест, переключение маршрутов и перезагрузка в этой сессии не выполняются.

## Ещё не подтверждено сквозным испытанием

- Установка новой версии root-помощника через парольный диалог, его запуск как LaunchDaemon и работа реального TUN.
- Реальное отключение питания/перезагрузка и запуск recovery LaunchAgent при следующем входе.
- Сон/пробуждение, смена Wi-Fi/Ethernet, включение новой сетевой службы уже после подключения, несколько GUI-экземпляров, длительный прогон.
- Доступность реальных серверов и передача TCP/UDP каждого протокола; успешный `check` этого не доказывает.
- Windows/Linux/Android: проверки macOS не являются подтверждением поведения этих платформ.
