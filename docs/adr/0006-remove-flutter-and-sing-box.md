# ADR-0006. Удалить Flutter-версию и sing-box из проекта

Статус: принято · 2026-11-16

## Контекст

- План ([PLAN.md](../migration/PLAN.md)) держал Flutter-версию в репозитории
  до этапа 6, как живой эталон поведения, а sing-box — как запасное ядро и
  тестовый сервер.
- С 2026-11-12 sing-box уже не входил в сборку macOS: приложение и помощник
  работают только через свой движок `gorion-engine` (ADR-0005). При этом в
  ядре остались запуск sing-box, его `check`, повтор подключения через него,
  флаг `singBoxOnly` в протоколе помощника, а в репозитории — загрузка
  бинарников sing-box, их замок с хешами и сквозные тесты против его сервера.
- Flutter-версия занимала `lib/`, `test/`, шесть платформенных папок,
  установщик Inno Setup и Dart-инструменты. В рабочей копии это ещё ~2 ГБ
  сборок и 325 МБ бинарников sing-box.
- Владелец решил оставить только нативное приложение со своим ядром и
  удалить всё лишнее.

## Варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| А. Ждать этапа 6, как в плане | эталон под рукой, `flutter test` можно запустить | два приложения в одном дереве, мёртвый код sing-box в ядре, агенты и люди путаются, что главное |
| Б. Удалить Flutter и sing-box целиком, эталон — в истории git | одно приложение, одно ядро, нет ветвлений «движок или sing-box» | паритет сверяется по `git show`; новые золотые фикстуры — из отдельной рабочей копии; совместимость протоколов, кроме XHTTP, больше не проверяется тестом против чужого сервера |
| В. Удалить Flutter, оставить sing-box как тестовый сервер | сквозные тесты остаются | sing-box всё равно нужно скачивать и проверять; владелец просил убрать его полностью |

## Решение

Вариант Б.

- Удалены `lib/`, `test/`, `android/`, `ios/`, `linux/`, `macos/` и
  `windows/` Flutter-версии, `pubspec.*`, установщик, Dart-инструменты
  (`export_golden`, `vendor_singbox`, `verify_macos_proxy`,
  `gen_design_tokens` — переписан на Python с тем же выводом), замок
  `tool/singbox.lock.json`, шрифты и картинки, которые нужны были только
  Flutter.
- Эталон поведения — коммит `166ab89`, последний, где лежат `lib/` и
  `test/`. Ссылки «Эталон: lib/…» в коде и пути в parity.md указывают туда.
- Ядро запускает только `gorion-engine`: выбор ядра (`CoreKind`,
  `GORION_CORE`), запуск и `check` sing-box, повтор через него удалены.
  Помощник — протокол 5 (`--engine` вместо `--singbox`, без `singBoxOnly`),
  при установке удаляет старую копию sing-box.
- Подписки в виде готового JSON sing-box больше не принимаются (Δ к
  эталону): принимаются ссылки, их списки (в том числе base64) и JSON Xray.
- Внутренняя конфигурация, которую строит ядро и читает движок, сохраняет
  схему JSON sing-box. Это формат данных, проверенный золотыми фикстурами,
  а не зависимость; называем его «конфигурация Gorion».
- Комментарии, где sing-box или Xray названы как образец поведения протокола
  (значения по умолчанию, порядок кадров), остаются: это ссылки на
  спецификацию, а не на код проекта.

## Последствия

- Проще: одно приложение, одно ядро, нет откатов и двух путей запуска;
  команды в AGENTS.md только нативные.
- Сложнее: сверка паритета — через `git show 166ab89:lib/…` или
  `git worktree add`; новые золотые фикстуры выгружаются там же.
- Пользователи с помощником протокола 3–4 увидят карточку «Обновить»: нужен
  пароль администратора.
- Подписки, которые провайдер отдаёт только в виде JSON sing-box, больше не
  добавятся; приложение просит ссылку для v2ray или Xray.
- Нужно вернуть сквозные проверки совместимости — стенд на сервере Xray для
  Shadowsocks, Trojan, VLESS, транспортов и Hysteria2
  ([engine-next.md](../migration/engine-next.md), пункт 10).
